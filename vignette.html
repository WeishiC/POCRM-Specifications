Introduction

The code in the POCRM-Specifications repository has been created to support the design of phase I dual-agent combination trials using the Partial Ordering Continual Reassessment Method (POCRM) [1]. The POCRM extends the Continual Reassessment Method (CRM) [2] to situations where the toxicity ordering of some dose combinations is unknown. It requires the trial team to specify a set of plausible complete orderings of the combinations and a toxicity skeleton before the trial starts. These two choices determine whether the design is consistent, i.e., whether it selects the true maximum tolerated combination (MTC) with probability one as the sample size grows, and they have a large impact on its performance at realistic sample sizes [3].

The code supports all the steps required to specify a POCRM design based on the consistency conditions derived in [3]:

  1. listing all possible orderings of the combinations;
  2. selecting a small set of orderings, either for a given set of toxicity scenarios (scenario-specific) or for any scenario (scenario-agnostic);
  3. checking and calibrating the toxicity skeleton against the consistency conditions;
  4. evaluating the operating characteristics of the resulting design by simulation.

Let’s consider a phase I trial combining two drugs, A and B, each with three dose levels. The nine combinations \(\tilde d_{i,j}=(a_i,b_j)\), \(i,j=1,2,3\), form a \(3\times3\) grid:

\(a_1\) \(a_2\) \(a_3\)
\(b_3\) \(\tilde d_{1,3}\) \(\tilde d_{2,3}\) \(\tilde d_{3,3}\)
\(b_2\) \(\tilde d_{1,2}\) \(\tilde d_{2,2}\) \(\tilde d_{3,2}\)
\(b_1\) \(\tilde d_{1,1}\) \(\tilde d_{2,1}\) \(\tilde d_{3,1}\)

Throughout, the combinations are indexed \(1,\ldots,9\) in the order \((\tilde d_{1,1}, \tilde d_{2,1}, \tilde d_{3,1}, \tilde d_{1,2}, \ldots, \tilde d_{3,3})\), i.e., the level of drug A changes fastest. A toxicity scenario is a vector of nine true toxicity probabilities in this order, and an ordering is a vector of combination indices, from the least to the most toxic. The target toxicity level (TTL) is \(\theta_0=0.3\). The nine scenarios below cover all possible locations of a single MTC on the grid; they are scenarios 1-9 in Table S1 of the Supplementary Materials of [3].

# true toxicity probabilities, combinations ordered (d11, d21, d31, d12, ..., d33)

  c(0.20,0.25,0.35, 0.30,0.40,0.50, 0.45,0.55,0.60),
  c(0.15,0.20,0.35, 0.25,0.30,0.40, 0.45,0.50,0.55),
  c(0.01,0.03,0.05, 0.10,0.15,0.30, 0.20,0.25,0.35),
  c(0.01,0.10,0.15, 0.05,0.20,0.25, 0.30,0.35,0.40),
  c(0.05,0.20,0.35, 0.10,0.25,0.40, 0.15,0.30,0.45),
  c(0.01,0.03,0.07, 0.05,0.15,0.20, 0.10,0.25,0.30))

# labels of the combinations, used in the output below
cnames <- paste0("(", rep(1:3, 3), ",", rep(1:3, each = 3), ")")

The full set of 19 scenarios used in [3], which also covers two and three MTCs, is stored in the RData folder of the repository.

Getting the code

The functions are provided as R scripts. After cloning or downloading the repository, they are loaded with source(). They depend on the dfcrm [4], pocrm [5], nnet, dplyr and combinat packages, which are available from CRAN.

# load R packages
library(dplyr)
library(ggplot2)
theme_set(theme_bw()) # sets up plotting theme

# functions from the POCRM-Specifications repository
source("ListOrder.R")      # ListOrder()

source("GetOrderScen.R")   # get.order.scen()

source("POCRM.R")          # pocrm.sim()

source("CheckPOCRM.R")     # CheckPOCRM()

Ordering Specification

Listing all orderings

Monotonicity of each single drug implies only a partial ordering of the combinations. For example, \(\tilde d_{1,1}\to\tilde d_{2,1}\to\tilde d_{3,1}\) is known, but the order of \(\tilde d_{2,1}\) and \(\tilde d_{1,2}\) is not. A complete ordering is an ordering of all nine combinations that respects the partial ordering. The function ListOrder() lists all complete orderings for a grid of any dimension:

orderings <- ListOrder(dim = c(3, 3))
dim(orderings)

Scenario-specific ordering specification

A key result of [3] is that the POCRM can only be consistent under a scenario if the included orderings contain at least one ordering from the correct ordering group of that scenario. An ordering belongs to the correct group if it places the MTC in its correct position and all combinations less toxic than the MTC before it. The orderings in the correct group need not be exactly correct: combinations below the MTC can be in any order among themselves.

The function get.order() searches for S orderings that cover the correct group under every scenario in all.scen. It draws S orderings at random until the coverage condition is met, up to max.sim draws, and returns NULL if no consistent set is found:

load("Rdata/scen3x3.RData")
set.seed(24601)
scen.spec <- get.order(max.sim = 1e+4, all.scen = scen, all.orderings = orderings,
                       TTL = TTL, S = 3)
scen.spec
##      d1 d2 d3 d4 d5 d6 d7 d8 d9
## [1,]  1  2  4  5  3  6  7  8  9
## [2,]  1  2  4  7  3  5  8  6  9
## [3,]  1  2  4  7  5  8  3  6  9

If NULL is returned, a larger S can be tried. The argument order.fix forces given orderings into the selection, which is useful if the clinical team considers some orderings particularly plausible.

The returned orderings are rows of orderings. To compare different choices, it is convenient to work with their row numbers:

row_id <- function(sel, all) apply(sel, 1, function(o) which(apply(all, 1, function(a) all(a == o))))
ord.spec <- row_id(scen.spec, orderings)
ord.spec
## [1] 11 18 21

The set of orderings recommended in [3] for the 19 scenarios is orderings 11, 16 and 23. Since get.order() is a random search, other consistent sets of the same size may be returned. Among several consistent sets, [3] recommends the one with the largest number of correct groups covered per ordering (\(N_\mathrm{consis}\)).

Scenario-agnostic ordering specification

In practice, the true scenario is unknown. Although the number of possible scenarios is infinite, the correct ordering group only depends on the order-scenario, i.e., on the MTC and the set of combinations less toxic than it, and there are finitely many order-scenarios. The function get.order.scen() lists one toxicity scenario per order-scenario, together with a set of candidate orderings rich enough for the selection:

order.scen <- get.order.scen(dim = c(3, 3), TTL = TTL)
nrow(order.scen$OrderScen)   # number of order-scenarios
## [1] 30

Applying get.order() to the order-scenarios gives orderings that cover the correct group under any scenario:

Skeleton Calibration

Initial skeleton

Covering the correct group is necessary but not sufficient for consistency. The toxicity skeleton must also satisfy two further conditions (Theorem 2 in [3]):

  • Condition 2: under every included incorrect ordering, the likelihood must favour an included correct ordering at the allocations of patients that the design can reach;
  • Condition 3: the CRM must be consistent under every included correct ordering.

A convenient starting point is the skeleton from getprior() in the dfcrm package [4]. Here we use the skeleton of Section 2 in [3]:

alpha0 <- c(0.10, 0.20, 0.30, 0.40, 0.45, 0.50, 0.54, 0.59, 0.64)

Condition 3: CRM consistency

Condition 2: likelihood comparison

Condition 2 compares the limiting likelihoods of an incorrect ordering \(\mathcal O_m\) and an included correct ordering \(\mathcal O_t\) over the allocations of patients that \(\mathcal O_m\) can produce asymptotically, i.e., allocations on the set \(\mathcal S(m;\mathbf R)\) of misordered combinations, the combinations adjacent to them, and the MTC. Each allocation is written as \(\boldsymbol\eta=(1-u)\boldsymbol\zeta+u\,\mathbf e_\nu\), where \(u\) is the proportion of patients at the MTC and \(\boldsymbol\zeta\) is an allocation over the other combinations in \(\mathcal S(m;\mathbf R)\). The condition is checked over a grid of \(u\) and \(\boldsymbol\zeta\) (Section 4.3 of [3]).

The function CheckPOCRM() performs this check for every included incorrect ordering under one scenario. It returns, for each pair, the smallest value of the left-hand side of Equation (2) in [3] over the grid, the allocation where it occurs, and whether the condition holds within the tolerance:

# check for scenario 5 
cond2 <- CheckPOCRM(skeleton=alpha0, R=scen[5,], orderings=orderings[ord.agn, ], ids = ord.agn,
                    TTL = TTL, cnames = cnames, seed = 24601)

  labs(x = "proportion of patients at the MTC (u)", y = "LHS of Equation (2)",

Empirically, the most effective way to fix a violation is to change the skeleton values directly involved, i.e., at the positions of the combinations in \(\mathcal S(m;\mathbf R)\) under \(\mathcal O_m\) and \(\mathcal O_t\), and to recheck Condition 3 afterwards.

alpha.agn <- c(0.17, 0.26, 0.32, 0.37, 0.38, 0.40, 0.41, 0.42, 0.48)
subset(CheckCRM_all(R=scen[5,], alpha=alpha.agn, orderings=orderings[ord.agn,]), !holds)

Note that the consistency conditions depend on the orderings included: a skeleton that is consistent for one set of orderings need not be consistent for another.

Design Evaluation

Operating Characteristics

The function pocrm.sim() simulates the two-stage POCRM [1].

scen <- scen[1:9,]
x0 <- 1:ncol(scen)    # stage-1 escalation path: by rows, d11 -> d21 -> d31 -> d12 -> ...
skel_matrix <- function(alpha, ids) getwm(orderings[ids, , drop = FALSE], alpha)

run_pcs <- function(alpha, ids, n = 60, nsim) {
  sapply(1:nrow(scen), function(s) {
    res <- pocrm.sim(r = scen[s, ], alpha = skel_matrix(alpha, ids),
                     prior.o = rep(1 / length(ids), length(ids)), x0 = x0,
                     stop = n + 1, n = n, theta = TTL, nsim = nsim)
    sum(res$MTD.selection[abs(scen[s, ] - TTL) < 1e-10])   # proportion of correct selection
  })
}

We compare the proportion of correct selection (PCS) at \(N=60\) patients for the scenario-specific 3 orderings and the Wages 6 orderings, both under the initial skeleton \(\boldsymbol\alpha^{(0)}\). The number of simulations is kept small here to keep the run time short; [3] uses \(10^4\) simulations.

pcs <- data.frame(scenario = factor(rep(1:9, 2)),
                  orderings = rep(c("Scenario-specific 3", "Wages 6"), each = 9),
                  PCS = c(run_pcs(alpha0, ord.spec, nsim=200), 
                          run_pcs(alpha0, ord.wages, nsim=200)))
geo_mean <- function(x) exp(mean(log(x)))
pcs_means <- pcs %>% group_by(orderings) %>%
  summarise(arithmetic = mean(PCS), geometric = geo_mean(PCS))
pcs_means

The difference is largest under scenario 5, where the Wages 6 orderings do not include any ordering from the correct group. On average, the difference is smaller, since the two specifications perform similarly under the scenarios where both cover the correct group.

Asymptotic behaviour

Consistency is an asymptotic property, and it can be checked by simulation by increasing the sample size. Under a consistent specification, the PCS approaches 100% under every scenario; under an inconsistent one, it levels off below 100% under some scenarios. As the run time grows with the sample size, the chunk below is not evaluated in this vignette:

Ns <- c(20, 60, 100, 500, 1000, 1e+4, 1e+5, 1e+6)
asym <- expand.grid(N = Ns, skeleton = c("alpha0", "alpha.agn"))
asym$PCS5 <- mapply(function(N, sk) {
  run_pcs(get(as.character(sk)), ord.agn, n = N, nsim = 500)[5]
}, asym$N, asym$skeleton)
ggplot(asym, aes(N, PCS5, colour = skeleton)) + geom_line() + scale_x_log10() +
  labs(y = "PCS under scenario 5", title = "PCS vs. sample size")

The functions BOIN::get.oc.comb() [8], SFD.sim() and BLRM.sim() (in SFD.R and BLRM.R) simulate the comparator designs used in [3] in the same way.
